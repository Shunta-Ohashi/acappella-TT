# ブラウザ確認用サンプル

## データの読み込み

保存データがない初回起動では、このサンプルを含むデモが自動で表示されます。
すでにlocalStorageにデータがある場合は、その内容を優先するため、新しいサンプルは自動追加されません。

1. 必要なデータがある場合は、まず「設定 → バックアップを書き出す」で退避します。
2. [サンプルJSON](../public/demo-browser-backup.json)を「設定 → バックアップから復元」で選びます。
   開発サーバーの `/demo-browser-backup.json` からも取得できます（例：`http://localhost:5173/demo-browser-backup.json`）。
3. 復元確認ダイアログで承認します。**復元は現在の全データを置き換えます。**
4. 「イベント」から「自動生成お試しライブ（2日開催）」を開き、Step 6「タイムテーブル・運営」へ進みます。

何度でも同じJSONから初期状態へ戻せます。確認終了後は、退避したバックアップを復元してください。
既存の「2026 デモライブ」「2026 学祭デモ」もJSONに含まれています。

## サンプルの構成

- 12月5日・6日の2日開催。各日Main StageとSub Stageがあります。
- Mainは1日目が3部、2日目が2部。Subには部がありません。
- 固定バンド4組が両日出演し、日ごとに別のEventBand・出演時間を持ちます。
- 掛け持ちメンバーを含む4人編成。部間と2日目Subに30分の明示的休憩を設けています。
- あおいは09:00〜11:00／13:00〜17:00の参加可能時間。2日目のしょうは参加未定、はやては欠席（出演なし）です。
- Main PA候補は「はる」「とも」、Sub PA候補は「さき」「なお」。出演者とは別の担当者です。
- 部内5分休憩・部間30分休憩、開始時刻14:00固定、先頭TT固定を含みます。
- 撮影の「こう」「りお」「すい」が同じ休憩を担当します。

初期状態は全イベントでERROR 0件・不正Stage 0件です。
2日目の「参加未定」は意図した注意情報であり、生成を妨げません。
両日の自動生成・適用後のvalidationとsnapshot復元は自動テストで確認しています。

## 確認する操作と期待結果

| 操作 | 確認ポイント |
| --- | --- |
| 1日目／Mainを開く | 第1部のMoonlightに先頭TT固定、第2部にBreezeと5分休憩、第3部はPoolのAmberが未配置。撮影列の休憩行に3名が表示される |
| 「この開催日を自動生成」 | まず設定ダイアログが開く。初回は部内／部間休憩ともON。「この条件で自動生成」で全Stageのプレビューが開き、Amberの配置とPA担当が提案される。適用まではTT・PAは変わらない |
| プレビューをキャンセル（またはEsc） | Pool、出演順、PA、Duty、TT固定は元のまま |
| 再生成して「この内容を適用」 | 1日目の4出演が配置され、PAが更新される。先頭TT固定・休憩・撮影3名は維持される |
| 2日目／Subを開く | Amberは14:00固定で配置済み。30分休憩があり、残り3出演は同日のPoolにある。1日目の出演がPoolへ混ざらない |
| 2日目を生成・適用 | 正常に適用でき、1日目のTT・PAには影響しない。参加未定の注意はblockingにならない |
| PA／当日運営を編集し、未保存で生成 | 未保存の変更がある旨が表示され、プレビューへ進まない。保存またはキャンセル後に再生成できる |
| 再読み込み | 適用済みTT・PA・Duty・TT固定が復元される。未保存のPA／Duty編集は保存されない |
| 部間休憩の削除／移動を試す | 参照・固定・休憩の制約に応じて防御や問題表示が働く。初期状態へはJSONから戻す |

1日目のPoolはAmber 1出演、2日目はMoonlight・Breeze・Prismの3出演から開始します。
生成プレビューは現在表示中Stageだけでなく、**選択中開催日の全Stage**が対象です。
候補の最適性やPA担当者の組み合わせを固定期待値にはせず、配置条件・保存後のERROR 0件を確認してください。

## 生成失敗の確認

Step 3でこのイベントの「はる」「とも」両方のMain PA担当可否を無効にして保存し、Step 6で生成します。
Main PA候補不足が説明され、TT・PAが勝手に置き換わらないことを確認できます。
確認後は担当可否を戻して保存するか、サンプルJSONから復元してください。

このデータは開発確認専用です。実在の団体・人物のデータではありません。

## 自動生成設定・TT初期化の追加確認

以下は1日目を対象に、サンプルJSONを復元した初期状態から確認します。
2日目は触らず、各操作の前後で出演配置・PA・休憩が変わっていないことも確認してください。

| 手順 | 期待結果 |
| --- | --- |
| 1. 「この開催日を自動生成」を押す | 「自動生成設定」が開く。初回は部内／部間休憩ともON |
| 2. 設定を変更してキャンセル／Esc | domainデータは変わらない。設定値は同じApp session内では記憶されるが、保存データには入らない |
| 3. 両方ONで「この条件で自動生成」 | プレビューに「部内休憩：保持／部間休憩：保持」と既存休憩が表示される |
| 4. プレビューをキャンセル／Esc | TT・Pool・PA・Duty・TT固定は変更されない |
| 5. 再生成して「この内容を適用」 | プレビューどおりのTTとPAが保存される。再生成の前に初期化する必要はない |
| 6. 初期状態に復元して部内休憩OFFで生成 | 撮影3名がその休憩を参照するため、当日運営の参照切れで生成を拒否するのが正常。Dutyや休憩は勝手に消えない |
| 7. 「この開催日のTTを初期化」を押す | 対象日・削除対象・保持対象・元に戻せないことを明記した確認ダイアログが開く |
| 8. 確認ダイアログをキャンセル／Esc | 全データは元のまま |
| 9. 再度開き「TTを初期化」を確定 | 1日目の全4出演が未配置Poolへ戻り、同日のPA・撮影担当3名・TT固定が消える |
| 10. 初期化後の設定を確認 | 部内／部間休憩、EventBand、出演条件・fixedPlacement、撮影／受付のDutyTypeは残る。選択中開催日・Stageも同じ |
| 11. 初期化直後に部内OFF・部間ONで生成 | 今度は休憩を参照するDutyがないので生成可能。プレビューから「第2部内の小休憩」が消え、部間休憩は残る |

| 13. 部間OFFも確認する | 下記の掛け持ち解消手順後、両方OFFで生成するとプレビューに部内／部間の既存休憩がない。適用したら同じ内容になる |

| 15. 初期化・適用後にreload | 最後に確定したTT・担当・TT固定が復元される。他日には変更がない |
| 16. 全ページで下へスクロール | 上部のAcappella TT／イベント／共通データ／設定ナビは画面外へスクロールする。イベント編集のStepナビも残らない |

### 部間休憩OFFの成功ケース

元のサンプルはMoonlightとBreeze、BreezeとAmberに掛け持ちメンバーがいます。
部間休憩を外すと、Section開始までの単なる空き時間は明示的休憩の代わりにならないため、生成失敗になることがあります。
これはHard constraintが維持されている正常な結果です。

OFFによる削除をプレビューまで確認したい場合は、次の順に操作してください。

1. 1日目のTTを初期化して確定します（休憩を参照する撮影担当も削除されます）。
2. Step 4で「Breeze（1日目）」を編集し、当日メンバーを「ひな」「はやて」の2人に変更して保存します。
   1日目は両者とも参加可能です。共通Band masterと2日目のBreezeは変更されません。
3. Step 6で部内／部間の両方をOFFにして生成します。プレビューから該当休憩が消えることを確認できます。
4. キャンセルではTTに休憩が残り、適用で削除されます。

この操作順は自動テストでも生成・最終検証の成功を確認しています。
必要なら1日目Sub Stageへ通常休憩を追加してから再生成し、両方OFFでもその通常休憩は残ることも確認できます。
休憩しか残っていない状態では、TT初期化ボタンはdisabledになります。
確認が終わったらサンプルJSONを復元して元の構成へ戻せます。
